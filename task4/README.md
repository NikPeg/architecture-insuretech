# Задание 4: Проектирование продажи ОСАГО

## Описание задачи

Спроектировать систему оформления ОСАГО онлайн с требованиями:
- Real-time отображение предложений от страховых компаний по мере поступления
- До 2500 одновременных пользователей в пик
- Максимальное время ожидания ответа от страховой — 60 секунд
- 5 страховых компаний предоставляют REST API

## Архитектурные решения

### 1. Сервис osago-aggregator

**Роль:** Отправка заявок в страховые компании и опрос решений для передачи результатов в core-app.

#### Требуется ли своё хранилище данных?

**Да**, собственная база данных PostgreSQL (`osago-aggregator-db`) для:
- **Заявок на ОСАГО** — сохранение информации о заявках клиентов
- **Предложений от страховых** — кэширование полученных результатов
- **Outbox-таблицы** — гарантированная публикация событий (паттерн Transactional Outbox)

**Обоснование:**
- Необходимость сохранять состояние заявок для аудита и повторной обработки
- Кэширование предложений для анализа
- Гарантия доставки событий при публикации в Kafka

#### Какой API предоставляет core-app?

**WebSocket API** (двунаправленный):

```
Операции:
- createOsagoApplication(vehicleData) → applicationId
- Stream<OsagoOffer> streamOffers(applicationId) 
- acceptOffer(applicationId, offerId) → result
```

**Обоснование:**
- Требование бизнеса: предложения должны отображаться сразу по мере получения
- WebSocket позволяет Server Push для real-time доставки
- Эффективное использование ресурсов при 2500 одновременных соединениях

### 2. Средство интеграции core-app ↔ osago-aggregator

**WebSocket** (внутреннее взаимодействие между сервисами)

**Почему:**
- Необходим двусторонний обмен данными
- Стриминг предложений от osago-aggregator к core-app в режиме реального времени
- Одно долгоживущее соединение эффективнее множества HTTP-запросов

### 3. API для веб-приложения в core-app

**WebSocket** (для операций ОСАГО) + **REST** (для остальных операций)

**WebSocket для ОСАГО:**
```javascript
// Создание заявки и получение real-time предложений
ws.send({ type: 'CREATE_OSAGO_APP', data: {...} });
ws.onmessage = (offer) => displayOffer(offer);
```

**REST для стандартных операций:**
- `GET /api/clients/{id}` — данные клиента
- `GET /api/policies` — список полисов

**Обоснование:**
- WebSocket для ОСАГО обеспечивает real-time UX согласно требованиям бизнеса
- REST достаточен для обычных CRUD-операций

### 4. Средство интеграции Web ↔ core-app

**WebSocket** (для ОСАГО) отмечен отдельной стрелкой на схеме с обозначением "WebSocket"

### 5. Паттерны отказоустойчивости

#### ⏱️ Rate Limiting (API Gateway)
- **Где:** API Gateway перед веб-приложением
- **Зачем:** Защита от перегрузки при 2500+ одновременных пользователей
- **Конфигурация:** 
  - На пользователя: 5 req/s
  - На IP: 50 req/s

#### ⏱️ Timeout (osago-aggregator → Страховые)
- **Где:** На каждом запросе к страховой компании
- **Зачем:** Соответствие требованию "макс. 60 секунд ожидания"
- **Конфигурация:** 60 секунд на запрос

#### 🔄 Retry (osago-aggregator → Страховые)
- **Где:** При временных сбоях связи со страховыми
- **Зачем:** Повышение надежности при сетевых проблемах
- **Конфигурация:** 3 попытки с exponential backoff (1s → 2s → 4s)

#### 🔒 Circuit Breaker (osago-aggregator → Страховые)
- **Где:** Отдельный для каждой страховой компании
- **Зачем:** Предотвращение каскадных сбоев, изоляция проблемных страховых
- **Конфигурация:**
  - Failure rate threshold: 50%
  - Wait duration in OPEN: 10s

#### 🏗️ Bulkhead (внутри osago-aggregator)
- **Где:** Изоляция пулов соединений для каждой страховой
- **Зачем:** Сбой одной страховой не влияет на работу с другими
- **Конфигурация:** Отдельный connection pool (max 20) для каждой из 5 страховых

### 6. Учёт множественных экземпляров сервисов

#### Проблемы и решения:

**WebSocket sticky sessions:**
- Load Balancer настроен на sticky sessions по session ID
- Клиент остается подключенным к одному экземпляру core-app

**Координация Circuit Breaker между экземплярами:**
- Shared Circuit Breaker state через Redis
- Все экземпляры osago-aggregator используют общее состояние

**Shared state для WebSocket:**
- Redis хранит mapping: session → pod
- Координация событий через Kafka

## Детальный flow работы Circuit Breaker

Circuit Breaker для каждой страховой компании имеет три состояния: CLOSED, OPEN, HALF_OPEN.

### Состояние 1: CLOSED (нормальная работа)

```
Запрос клиента → osago-aggregator → [Circuit Breaker: CLOSED] → Страховая компания
                                     ↓
                                  Подсчет ошибок в sliding window
                                  (например, последние 100 запросов)
```

**Поведение:**
- Все запросы проходят через Circuit Breaker к страховой компании
- Circuit Breaker подсчитывает успешные и неудачные запросы
- Если failure rate < 50% → остаемся в CLOSED

**Пример:**
```
Запросы: [✓ ✓ ✗ ✓ ✓ ✓ ✓ ✓ ✓ ✓]
Failure rate: 10% (1 ошибка из 10)
Состояние: CLOSED (продолжаем работу)
```

### Состояние 2: OPEN (отказ, circuit открыт)

**Триггер перехода:** Failure rate ≥ 50% в последних 100 запросах

```
Запрос клиента → osago-aggregator → [Circuit Breaker: OPEN] ✗
                                     ↓
                                  Немедленный отказ
                                  (без вызова страховой)
                                  ↓
                               Возврат fallback-ответа
```

**Поведение:**
- ❌ Запросы к страховой НЕ отправляются
- ⚡ Немедленный ответ клиенту (без ожидания timeout'а)
- 🕐 Wait duration: 10 секунд до попытки восстановления
- 📊 Клиент получает информацию: "Страховая компания X временно недоступна"

**Пример сценария:**
```
1. Failure rate достиг 52% (52 ошибки из 100 запросов)
2. Circuit Breaker переходит в OPEN
3. Следующие 50 запросов клиентов:
   - НЕ отправляются в страховую компанию
   - Получают мгновенный ответ: "unavailable"
   - Время ответа: 1-5ms вместо 60 секунд timeout
4. Через 10 секунд → переход в HALF_OPEN
```

**Преимущества OPEN состояния:**
- ✅ Защита страховой компании от дополнительной нагрузки
- ✅ Быстрый ответ пользователям (не ждем timeout)
- ✅ Экономия ресурсов osago-aggregator
- ✅ Другие страховые компании продолжают работать

### Состояние 3: HALF_OPEN (проверка восстановления)

**Триггер перехода:** Wait duration (10 секунд) после OPEN истек

```
Запрос клиента → osago-aggregator → [Circuit Breaker: HALF_OPEN]
                                     ↓
                                  Пропускаем ограниченное
                                  количество запросов (например, 10)
                                  ↓
                                  Страховая компания
                                  ↓
                            Анализ результатов
```

**Поведение:**
- 🔬 Пропускаем пробные запросы (например, 10 штук)
- 📊 Считаем failure rate на этих запросах
- ⚖️ Принимаем решение:
  - Если failure rate < 50% → CLOSED (восстановление)
  - Если failure rate ≥ 50% → OPEN (еще не восстановилась)

**Пример сценария восстановления:**
```
Время: T0
Состояние: OPEN (страховая компания упала)

Время: T0 + 10 секунд
Состояние: HALF_OPEN
Действие: Отправляем 10 пробных запросов

Вариант A (успешное восстановление):
Результаты: [✓ ✓ ✓ ✓ ✓ ✓ ✓ ✓ ✗ ✓]
Failure rate: 10%
Решение: → CLOSED (восстановление успешно)

Вариант B (страховая все еще недоступна):
Результаты: [✗ ✗ ✗ ✗ ✓ ✗ ✗ ✗ ✗ ✗]
Failure rate: 90%
Решение: → OPEN на следующие 10 секунд
```

### Полный flow для пользователя при отказе страховой

**Сценарий:** Страховая компания "Альфа" начала отвечать с ошибками

#### T0: Нормальная работа (CLOSED)
```
Пользователь Иван создает заявку ОСАГО
  ↓
osago-aggregator отправляет запросы в 5 страховых:
  ✓ Альфа: предложение 12,000 руб (200ms)
  ✓ Бета: предложение 11,500 руб (150ms)
  ✓ Гамма: предложение 12,500 руб (300ms)
  ✓ Дельта: предложение 11,800 руб (180ms)
  ✓ Эпсилон: предложение 13,000 руб (250ms)
  ↓
Иван видит все 5 предложений через WebSocket
```

#### T1: Начало проблем у "Альфа" (CLOSED → много ошибок)
```
Пользователь Мария создает заявку ОСАГО
  ↓
osago-aggregator отправляет запросы:
  ✗ Альфа: Timeout 60 секунд (страховая не отвечает)
  ✓ Бета: предложение 11,600 руб
  ✓ Гамма: предложение 12,400 руб
  ✓ Дельта: предложение 11,900 руб
  ✓ Эпсилон: предложение 12,800 руб
  ↓
Мария видит 4 предложения (Альфа пропущена после timeout)
```

#### T2: Circuit Breaker открывается (CLOSED → OPEN)
```
После 52 неудачных запросов к "Альфа" из 100:
Circuit Breaker переходит в OPEN для "Альфа"

Пользователь Петр создает заявку ОСАГО
  ↓
osago-aggregator:
  ⚡ Альфа: SKIP (Circuit OPEN) - мгновенный ответ
  ✓ Бета: предложение 11,700 руб
  ✓ Гамма: предложение 12,300 руб
  ✓ Дельта: предложение 12,000 руб
  ✓ Эпсилон: предложение 12,900 руб
  ↓
Петр видит 4 предложения СРАЗУ (не ждем 60 секунд)
UI показывает: "Предложение от Альфа временно недоступно"
```

**Преимущества для пользователя:**
- ✅ Получил 4 предложения вместо 0
- ✅ Время ответа: ~500ms вместо 60+ секунд
- ✅ Может оформить страховку в другой компании
- ✅ Понятное сообщение о недоступности

#### T3: Попытка восстановления (OPEN → HALF_OPEN)
```
Через 10 секунд Circuit Breaker переходит в HALF_OPEN

Пользователь Анна создает заявку ОСАГО
  ↓
osago-aggregator:
  🔬 Альфа: Пробный запрос (HALF_OPEN)
     → Если успех: Circuit → CLOSED
     → Если ошибка: Circuit → OPEN на 10 сек
  ✓ Остальные страховые работают как обычно
```

### Мониторинг состояний Circuit Breaker

**Метрики для отслеживания:**
```kotlin
// Пример метрик Prometheus для Circuit Breaker
resilience4j_circuitbreaker_state{name="insurance-alfa"} = 0  // CLOSED
resilience4j_circuitbreaker_state{name="insurance-beta"} = 0  // CLOSED
resilience4j_circuitbreaker_state{name="insurance-alfa"} = 1  // OPEN
resilience4j_circuitbreaker_state{name="insurance-alfa"} = 2  // HALF_OPEN

resilience4j_circuitbreaker_failure_rate{name="insurance-alfa"} = 0.52  // 52%
resilience4j_circuitbreaker_calls_total{name="insurance-alfa",kind="successful"} = 48
resilience4j_circuitbreaker_calls_total{name="insurance-alfa",kind="failed"} = 52
```

**Алерты:**
```yaml
# Prometheus Alert Rules
- alert: CircuitBreakerOpen
  expr: resilience4j_circuitbreaker_state == 1
  for: 1m
  annotations:
    summary: "Circuit Breaker открыт для {{ $labels.name }}"
    description: "Страховая компания {{ $labels.name }} недоступна"

- alert: HighFailureRate
  expr: resilience4j_circuitbreaker_failure_rate > 0.3
  for: 2m
  annotations:
    summary: "Высокий процент ошибок для {{ $labels.name }}"
    description: "Failure rate: {{ $value }}%"
```

## Преимущества решения

✅ **Real-time UX:** Предложения отображаются немедленно по мере получения  
✅ **Высокая отказоустойчивость:** 5 паттернов защиты на разных уровнях  
✅ **Масштабируемость:** Горизонтальное масштабирование всех компонентов  
✅ **Производительность:** WebSocket эффективнее множества HTTP-запросов  
✅ **Изоляция:** Сбой одной страховой не влияет на другие (Bulkhead + Circuit Breaker)
