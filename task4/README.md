# Задание 4: Проектирование продажи ОСАГО

## Описание задачи

Спроектировать систему оформления ОСАГО онлайн с требованиями:
- Real-time отображение предложений от страховых компаний по мере поступления
- До 2500 одновременных пользователей в пик
- Максимальное время ожидания ответа от страховой — 60 секунд
- 5 страховых компаний предоставляют REST API

## Архитектурные решения

### 1. Сервис osago-aggregator

**Роль:** Отправка заявок в страховые компании и опрос решений для передачи результатов в core-app.

#### Требуется ли своё хранилище данных?

**Да**, собственная база данных PostgreSQL (`osago-aggregator-db`) для:
- **Заявок на ОСАГО** — сохранение информации о заявках клиентов
- **Предложений от страховых** — кэширование полученных результатов
- **Outbox-таблицы** — гарантированная публикация событий (паттерн Transactional Outbox)

**Обоснование:**
- Необходимость сохранять состояние заявок для аудита и повторной обработки
- Кэширование предложений для анализа
- Гарантия доставки событий при публикации в Kafka

#### Какой API предоставляет core-app?

**WebSocket API** (двунаправленный):

```
Операции:
- createOsagoApplication(vehicleData) → applicationId
- Stream<OsagoOffer> streamOffers(applicationId) 
- acceptOffer(applicationId, offerId) → result
```

**Обоснование:**
- Требование бизнеса: предложения должны отображаться сразу по мере получения
- WebSocket позволяет Server Push для real-time доставки
- Эффективное использование ресурсов при 2500 одновременных соединениях

### 2. Средство интеграции core-app ↔ osago-aggregator

**WebSocket** (внутреннее взаимодействие между сервисами)

**Почему:**
- Необходим двусторонний обмен данными
- Стриминг предложений от osago-aggregator к core-app в режиме реального времени
- Одно долгоживущее соединение эффективнее множества HTTP-запросов

### 3. API для веб-приложения в core-app

**WebSocket** (для операций ОСАГО) + **REST** (для остальных операций)

**WebSocket для ОСАГО:**
```javascript
// Создание заявки и получение real-time предложений
ws.send({ type: 'CREATE_OSAGO_APP', data: {...} });
ws.onmessage = (offer) => displayOffer(offer);
```

**REST для стандартных операций:**
- `GET /api/clients/{id}` — данные клиента
- `GET /api/policies` — список полисов

**Обоснование:**
- WebSocket для ОСАГО обеспечивает real-time UX согласно требованиям бизнеса
- REST достаточен для обычных CRUD-операций

### 4. Средство интеграции Web ↔ core-app

**WebSocket** (для ОСАГО) отмечен отдельной стрелкой на схеме с обозначением "WebSocket"

### 5. Паттерны отказоустойчивости

#### ⏱️ Rate Limiting (API Gateway)
- **Где:** API Gateway перед веб-приложением
- **Зачем:** Защита от перегрузки при 2500+ одновременных пользователей
- **Конфигурация:** 
  - На пользователя: 5 req/s
  - На IP: 50 req/s

#### ⏱️ Timeout (osago-aggregator → Страховые)
- **Где:** На каждом запросе к страховой компании
- **Зачем:** Соответствие требованию "макс. 60 секунд ожидания"
- **Конфигурация:** 60 секунд на запрос

#### 🔄 Retry (osago-aggregator → Страховые)
- **Где:** При временных сбоях связи со страховыми
- **Зачем:** Повышение надежности при сетевых проблемах
- **Конфигурация:** 3 попытки с exponential backoff (1s → 2s → 4s)

#### 🔒 Circuit Breaker (osago-aggregator → Страховые)
- **Где:** Отдельный для каждой страховой компании
- **Зачем:** Предотвращение каскадных сбоев, изоляция проблемных страховых
- **Конфигурация:**
  - Failure rate threshold: 50%
  - Wait duration in OPEN: 10s

#### 🏗️ Bulkhead (внутри osago-aggregator)
- **Где:** Изоляция пулов соединений для каждой страховой
- **Зачем:** Сбой одной страховой не влияет на работу с другими
- **Конфигурация:** Отдельный connection pool (max 20) для каждой из 5 страховых

### 6. Учёт множественных экземпляров сервисов

#### Проблемы и решения:

**WebSocket sticky sessions:**
- Load Balancer настроен на sticky sessions по session ID
- Клиент остается подключенным к одному экземпляру core-app

**Координация Circuit Breaker между экземплярами:**
- Shared Circuit Breaker state через Redis
- Все экземпляры osago-aggregator используют общее состояние

**Shared state для WebSocket:**
- Redis хранит mapping: session → pod
- Координация событий через Kafka

### Обозначения на схеме:

- ⏱️ — Timeout / Rate Limiter
- 🔄 — Retry  
- 🔒 — Circuit Breaker
- 🏗️ — Bulkhead

### Типы соединений:

- **Сплошная линия** (→) — синхронное REST
- **Двойная линия** (WebSocket) — двунаправленный real-time обмен
- **Пунктир** (-.→) — асинхронное / периодическое

## Преимущества решения

✅ **Real-time UX:** Предложения отображаются немедленно по мере получения  
✅ **Высокая отказоустойчивость:** 5 паттернов защиты на разных уровнях  
✅ **Масштабируемость:** Горизонтальное масштабирование всех компонентов  
✅ **Производительность:** WebSocket эффективнее множества HTTP-запросов  
✅ **Изоляция:** Сбой одной страховой не влияет на другие (Bulkhead + Circuit Breaker)

## Технологический стек

- **Backend:** Kotlin + Spring Boot
- **WebSocket:** Spring WebSocket
- **Event Streaming:** Apache Kafka
- **Database:** PostgreSQL
- **Cache/State:** Redis
- **Load Balancer:** NGINX с sticky sessions
- **Resilience:** Resilience4j (Circuit Breaker, Retry, Timeout, Bulkhead)
