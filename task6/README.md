# Задание 6. Настройка Rate Limiting

## Описание проблемы

Один из партнёров InsureTech превышает согласованное количество запросов (20 RPS), достигая 250 RPS на все операции. Это приводит к нарушению SLA для других B2B-клиентов и снижает производительность всего приложения.

## Решение

Реализован паттерн **Rate Limiting** на уровне балансировщика NGINX. Это позволяет:
- Контролировать количество запросов от партнёров
- Защитить систему от перегрузки
- Обеспечить справедливое распределение ресурсов между всеми клиентами
- Предотвратить нарушение SLA для других партнёров

## Реализация

### Конфигурация NGINX

В файле `nginx.conf` настроено ограничение:
- **Лимит**: максимум 10 запросов в минуту
- **Идентификатор**: IP-адрес клиента (`$binary_remote_addr`)
- **Алгоритм**: счётчик фиксированного окна (встроенный в NGINX)
- **Код ошибки**: 429 (Too Many Requests) при превышении лимита

### Ключевые директивы

1. **`limit_req_zone`** - определяет параметры ограничения:
   ```nginx
   limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/m;
   ```
   - `$binary_remote_addr` - использует IP-адрес клиента как ключ для идентификации
   - `zone=api_limit:10m` - создаёт зону памяти размером 10МБ (достаточно для ~160 000 IP-адресов)
   - `rate=10r/m` - устанавливает лимит в 10 запросов в минуту

2. **`limit_req`** - применяет ограничение к конкретному location:
   ```nginx
   limit_req zone=api_limit;
   ```

3. **`limit_req_status`** - задаёт код HTTP-ошибки:
   ```nginx
   limit_req_status 429;
   ```
   По умолчанию NGINX возвращает код 503, но стандарт RFC 6585 предполагает использование кода 429 (Too Many Requests) для ситуаций превышения лимита запросов.

## Преимущества выбранного подхода

1. **Размещение на уровне балансировщика**:
   - Запросы фильтруются до попадания в приложение
   - Экономия ресурсов backend-серверов
   - Единая точка контроля для всех запросов

2. **Использование IP-адреса как идентификатора**:
   - Простота реализации
   - Подходит для B2B-клиентов с фиксированными IP
   - Низкие требования к памяти

3. **Низкое влияние на производительность**:
   - Алгоритм счётчика фиксированного окна эффективен
   - Минимальные накладные расходы
   - Быстрая обработка запросов

## Альтернативные подходы

Для более гибкой настройки можно рассмотреть:

1. **Лимитирование по API-ключу**:
   ```nginx
   limit_req_zone $http_api_key zone=api_limit:10m rate=20r/s;
   ```
   Позволит установить разные лимиты для разных партнёров.

2. **Использование burst и nodelay**:
   ```nginx
   limit_req zone=api_limit burst=5 nodelay;
   ```
   Позволяет обрабатывать кратковременные всплески нагрузки.

3. **Разные лимиты для разных endpoint'ов**:
   ```nginx
   location /search/ {
       limit_req zone=search_limit;
   }
   
   location /order/ {
       limit_req zone=order_limit;
   }
   ```

## Мониторинг

Для отслеживания эффективности Rate Limiting рекомендуется:
- Логировать запросы с кодом 429
- Мониторить количество заблокированных запросов
- Анализировать распределение запросов по IP-адресам
- Настроить алерты при массовых блокировках
