## Обоснование архитектурных решений

### Анализ требований
- **Доступность**: 99,9% (≈ 8.76 часов простоя в год)
- **RTO**: 45 минут (максимальное время восстановления)
- **RPO**: 15 минут (максимальная потеря данных)
- **Нагрузка**: поддержка клиентов из всех часовых поясов РФ, равномерное время отклика
- **Объем данных**: 50 GB (на текущий момент)

### Выбор фейловер-стратегии

**Решение: Active-Active с георезервированием**

#### Обоснование:
1. **Требования к доступности 99,9%** и **RTO 45 минут** соответствуют критериям для использования Active-Active стратегии
2. **Active-Active** обеспечивает:
   - Минимальное время простоя (стремится к нулю)
   - Частичную доступность даже при сбое одного узла
   - Равномерное распределение нагрузки
   - Лучшее масштабирование для высоконагруженных систем

3. **Георезервирование** (2 зоны доступности) обеспечивает:
   - Защиту от локальных сбоев и катастроф
   - Равномерное время отклика для пользователей из разных регионов РФ
   - Соответствие требованию обслуживания клиентов из всех часовых поясов

## Архитектурные решения

### 1. Конфигурация развертывания Kubernetes

**Решение: Независимые кластеры в каждой зоне доступности**

#### Обоснование:
- **Изоляция сбоев**: отказ в одном кластере не влияет на другой
- **Упрощение управления**: независимые обновления и масштабирование
- **Снижение зависимости от сетевой связности**: особенно важно для географически распределенных ЦОД
- **Гибкость**: возможность использовать разные конфигурации в зависимости от локальной нагрузки

#### Конфигурация каждого кластера:
- **Multi-master setup**: 3 master-узла для высокой доступности control plane
- **Worker nodes**: минимум 3 узла, распределенные по разным стойкам/rack'ам
- **Автомасштабирование**: Cluster Autoscaler + HPA (Horizontal Pod Autoscaler)

### 2. Балансировка нагрузки

**Многоуровневая балансировка:**

#### Уровень 1: GSLB (Global Server Load Balancer)
- **Назначение**: распределение трафика между зонами доступности
- **Функции**:
  - DNS-based routing с учетом географии пользователя
  - Health check для каждой зоны доступности
  - Failover на резервную зону при недоступности основной
- **Проверки доступности**: HTTP/HTTPS health check каждые 10 секунд

#### Уровень 2: Внешний Load Balancer (в каждой зоне)
- **Тип**: L7 Load Balancer (Application Load Balancer)
- **Функции**:
  - SSL/TLS termination
  - Распределение трафика между узлами Kubernetes кластера
  - Health check для Kubernetes Ingress
- **Проверки**: TCP health check каждые 5 секунд на Ingress endpoints

#### Уровень 3: Kubernetes Ingress Controller
- **Решение**: NGINX Ingress Controller (в каждом кластере)
- **Функции**:
  - Маршрутизация на уровне приложения
  - Rate limiting для защиты от перегрузки
  - Health check для сервисов и подов
- **Проверки**: readiness и liveness probes для каждого пода

#### Уровень 4: Kubernetes Service (в каждом namespace)
- **Тип**: ClusterIP для внутренних сервисов
- **Функции**:
  - Распределение нагрузки между подами одного сервиса
  - Service discovery внутри кластера

### 3. Стратегия масштабирования

**Горизонтальное масштабирование (основная стратегия)**

#### Для приложений (core-app, client-info, ins-product-aggregator):
- **HPA (Horizontal Pod Autoscaler)**:
  - Масштабирование по CPU: target 70%
  - Масштабирование по Memory: target 80%
  - Масштабирование по RPS (custom metric): target 100 RPS на под
  - Min replicas: 3 (в каждой зоне)
  - Max replicas: 20 (в каждой зоне)

#### Для кластера:
- **Cluster Autoscaler**:
  - Автоматическое добавление нод при нехватке ресурсов
  - Автоматическое удаление неиспользуемых нод (в нерабочие часы)
  - Min nodes: 3, Max nodes: 15 (в каждой зоне)

### 4. Конфигурация базы данных

**Решение: PostgreSQL с Patroni в конфигурации Active-Active (Multi-Master)**

#### Архитектура:

**ЦОД-1 (Primary) <-> ЦОД-2 (Secondary):**
- PostgreSQL Master + Patroni (в каждой зоне) - синхронная репликация между зонами
- PostgreSQL Replica + Patroni (по 2 в каждой зоне) - асинхронная репликация от Master

#### Компоненты:
1. **PostgreSQL с Patroni** (в каждой зоне):
   - 1 Master узел
   - 2 Replica узла для чтения
   - Автоматический failover при сбое Master
   - Синхронная репликация между зонами для Master
   - Асинхронная репликация для Replica

2. **etcd cluster** (для Patroni):
   - 3 узла в каждой зоне
   - Хранение состояния кластера БД
   - Координация между Patroni экземплярами

3. **HAProxy** (в каждой зоне):
   - Единая точка входа для приложений
   - Автоматическое переключение между Master и Replica
   - Health check через Patroni API
   - Read/Write split: запись на Master, чтение на Replica

4. **pgBackRest**:
   - Автоматические инкрементные бэкапы каждые 15 минут (RPO = 15 мин)
   - Полные бэкапы раз в день
   - Хранение бэкапов в S3-совместимом хранилище
   - Retention: 30 дней для инкрементных, 90 дней для полных

#### Обеспечение RPO и RTO:
- **RPO 15 минут**: инкрементные бэкапы каждые 15 минут + синхронная репликация
- **RTO 45 минут**: 
  - Автоматический failover Patroni: 1-2 минуты
  - Ручное восстановление из бэкапа (worst case): до 30 минут для 50GB
  - Время на проверку консистентности и переключение: 10-15 минут

#### Шардирование БД:
**Решение: НЕ применять шардирование на текущем этапе**

**Обоснование**:
- Текущий объем данных: 50 GB - легко обрабатывается одним кластером PostgreSQL
- Шардирование значительно усложняет архитектуру и разработку
- PostgreSQL с правильной настройкой и индексами легко обрабатывает такой объем
- Рекомендация: рассмотреть шардирование при достижении 500+ GB или специфических проблем с производительностью

**План на будущее**:
- Мониторинг размера БД и производительности
- При необходимости использовать Citus для горизонтального шардирования PostgreSQL
- Возможное разделение: по регионам, по типам страховых продуктов

### 5. Disaster Recovery Plan (DRP)

#### Сценарий 1: Отказ одного пода приложения
- **Обнаружение**: Kubernetes liveness probe (10 сек)
- **Действие**: Автоматический перезапуск пода
- **Время восстановления**: 30-60 секунд
- **Ответственный**: Kubernetes (автоматически)

#### Сценарий 2: Отказ узла Kubernetes
- **Обнаружение**: Kubernetes node health check (30 сек)
- **Действие**: Автоматический перенос подов на здоровые узлы
- **Время восстановления**: 2-3 минуты
- **Ответственный**: Kubernetes (автоматически)

#### Сценарий 3: Отказ Master БД в одной зоне
- **Обнаружение**: Patroni health check (10 сек)
- **Действие**: Автоматическое переключение на Replica через Patroni
- **Время восстановления**: 1-2 минуты
- **Ответственный**: Patroni (автоматически)
- **Оповещение**: Команда DevOps для анализа причин

#### Сценарий 4: Полный отказ одной зоны доступности
- **Обнаружение**: GSLB health check (10 сек), мониторинг
- **Действие**: GSLB автоматически перенаправляет весь трафик на вторую зону
- **Время восстановления**: 10-30 секунд (DNS propagation)
- **Ответственный**: GSLB (автоматически), команда DevOps на связи
- **Действия команды**:
  1. Подтверждение инцидента (5 мин)
  2. Оценка масштаба проблемы (10 мин)
  3. Масштабирование ресурсов во второй зоне при необходимости (15 мин)
  4. Начало восстановления первой зоны

#### Сценарий 5: Отказ обеих зон (катастрофический сценарий)
- **Обнаружение**: Мониторинг, алерты
- **Действия**:
  1. Объявление инцидента (немедленно)
  2. Оценка повреждений обеих площадок (15 мин)
  3. Решение о восстановлении: 
     - Быстрое восстановление одной из зон
     - Или развертывание в новой зоне из бэкапа
  4. Восстановление БД из последнего бэкапа (20-30 мин для 50GB)
  5. Развертывание приложений (10 мин)
  6. Проверка консистентности и тестирование (10 мин)
- **Время восстановления**: Целевое RTO 45 минут
- **Потеря данных**: Максимум 15 минут (RPO)
- **Ответственные**: Команда DevOps, Архитектор, CTO

### 6. Тестирование отказоустойчивости (Chaos Engineering)

Для обеспечения реальной готовности системы к сбоям необходимо регулярно проводить тесты отказоустойчивости с использованием принципов Chaos Engineering.

#### Цели Chaos Engineering:
- Проверка автоматических механизмов восстановления
- Выявление слабых мест в архитектуре до реальных инцидентов
- Повышение уверенности команды в отказоустойчивости системы
- Улучшение документации и runbook'ов

#### Инструменты:
- **Chaos Mesh** (для Kubernetes) - основной инструмент
- **Litmus** - альтернатива для Kubernetes
- **Gremlin** - коммерческое решение с расширенными возможностями

#### Типы экспериментов:

**1. Pod Chaos (каждую неделю):**
- Случайное удаление подов приложений
- Проверка работы readiness/liveness probes
- Проверка автоматического перезапуска
- **Ожидаемый результат**: RTO < 60 секунд, пользователи не заметили

**2. Network Chaos (раз в 2 недели):**
- Искусственные задержки сети между зонами (100-500ms)
- Потеря пакетов (5-10%)
- Отказ сетевого соединения между компонентами
- **Ожидаемый результат**: система продолжает работать, возможна деградация производительности

**3. Node Chaos (раз в месяц):**
- Отключение worker-узлов Kubernetes
- Проверка работы Cluster Autoscaler
- Проверка перемещения подов на другие узлы
- **Ожидаемый результат**: RTO < 3 минуты, автоматическое восстановление

**4. Database Chaos (раз в квартал):**
- Отказ Master БД (проверка Patroni failover)
- Задержка репликации между зонами
- Проверка восстановления из бэкапа
- **Ожидаемый результат**: RTO < 2 минуты для failover, RPO < 15 минут

**5. Zone Chaos (раз в полгода):**
- Полное отключение одной зоны доступности
- Проверка GSLB failover
- Проверка нагрузки на оставшуюся зону
- **Ожидаемый результат**: RTO < 30 секунд, доступность сохранена

**6. Full DR Drill (раз в год):**
- Катастрофический сценарий: обе зоны недоступны
- Восстановление из бэкапов в новой зоне
- Проверка всех процедур Disaster Recovery
- **Ожидаемый результат**: RTO < 45 минут согласно требованиям

#### Процесс проведения экспериментов:

1. **Планирование**:
   - Определение гипотезы (что проверяем)
   - Определение steady state (нормальное состояние системы)
   - Выбор времени проведения (желательно в рабочие часы под наблюдением)

2. **Подготовка**:
   - Уведомление команды
   - Проверка работы мониторинга и алертинга
   - Подготовка процедур отката

3. **Выполнение**:
   - Запуск chaos эксперимента
   - Наблюдение за метриками и поведением системы
   - Фиксация всех отклонений

4. **Анализ**:
   - Проверка гипотезы (подтверждена или опровергнута)
   - Анализ логов и метрик
   - Выявление проблем и узких мест

5. **Улучшение**:
   - Создание задач на устранение выявленных проблем
   - Обновление документации
   - Планирование следующих экспериментов

#### Метрики успешности Chaos Engineering:
- **MTTR** (Mean Time To Recovery): среднее время восстановления после экспериментов
- **Blast Radius**: радиус влияния сбоев (должен быть минимален)
- **False Positive Rate**: частота ложных алертов
- **Team Confidence**: уровень уверенности команды в системе (опросы)

### 7. Мониторинг и алертинг

#### Стек мониторинга:
- **Prometheus**: сбор метрик с приложений и инфраструктуры
- **Grafana**: визуализация метрик, дашборды
- **Alertmanager**: управление алертами
- **Loki**: сбор и анализ логов
- **Jaeger**: distributed tracing

#### Ключевые метрики:
1. **Доступность**:
   - Uptime сервисов
   - Успешность health checks
   - Доступность зон

2. **Производительность**:
   - Latency (p50, p95, p99)
   - RPS
   - Error rate

3. **Ресурсы**:
   - CPU, Memory utilization
   - Disk I/O
   - Network throughput

4. **База данных**:
   - Connection pool utilization
   - Query latency
   - Replication lag
   - Transaction rate

#### Алерты:
- **Critical**: 
  - Доступность < 99%
  - Error rate > 5%
  - Replication lag > 30 секунд
  - Отказ зоны доступности
  
- **Warning**:
  - CPU > 80%
  - Memory > 85%
  - Disk usage > 80%
  - Response time p95 > 500ms

### 8. Безопасность

#### Network Security:
- **Межзональное взаимодействие**: VPN между ЦОД
- **Firewall**: разрешен только необходимый трафик
- **DDoS protection**: на уровне GSLB и внешнего LB

#### Application Security:
- **TLS/SSL**: шифрование всего трафика (in-transit)
- **Secrets management**: Kubernetes Secrets + External Secrets Operator
- **RBAC**: строгие права доступа в Kubernetes

#### Data Security:
- **Encryption at rest**: шифрование дисков БД
- **Backup encryption**: шифрованные бэкапы
- **Compliance**: соответствие требованиям по защите персональных данных

## Ожидаемые результаты

### Доступность:
- **Целевая доступность**: 99,9% (8.76 часов простоя в год)
- **Фактическая ожидаемая**: 99,95%+ (благодаря Active-Active и георезервированию)

### Производительность:
- **Latency**: p95 < 200ms для всех регионов
- **RPS**: до 1000+ RPS (с автомасштабированием)
- **Scalability**: горизонтальное масштабирование до 20 подов на сервис

### Отказоустойчивость:
- **RTO**: 1-2 минуты для большинства сценариев, до 45 минут для катастрофических
- **RPO**: 15 минут максимум
- **Failover**: автоматический в большинстве случаев

### Стоимость:
- **Оптимизация**: Cluster Autoscaler снижает затраты в периоды низкой нагрузки
- **Прогнозируемость**: четкое понимание стоимости инфраструктуры
- **ROI**: снижение потерь от простоев значительно превышает затраты на инфраструктуру
