# InsureTech: Архитектура высоконагруженной страховой платформы

Проект посвящён разработке технологической архитектуры для страховой компании InsureTech, которая столкнулась с проблемами производительности и отказоустойчивости при росте нагрузки.

## 📋 Описание проекта

InsureTech — это онлайн-платформа для продажи страховых продуктов, которая агрегирует предложения от нескольких страховых компаний и предоставляет единый интерфейс для клиентов. В процессе роста бизнеса возникли следующие вызовы:

- Необходимость обеспечения доступности 99.9% с минимальным временем восстановления
- Нестабильная работа в периоды пиковой нагрузки
- Зависимость сервисов друг от друга, приводящая к каскадным сбоям
- Планируемое увеличение количества страховых компаний с 5 до 10
- Высокая вариативность запрашиваемых данных
- Проблемы с партнёрами, превышающими лимиты запросов

## Решённые задачи

### [Task 1: Проектирование технологической архитектуры](./task1/)

**Цель:** Спроектировать архитектуру с высокой доступностью и отказоустойчивостью.

**Требования:**
- Доступность: 99.9%
- RTO: 45 минут
- RPO: 15 минут
- Масштабирование и географическое распределение

**Решение:**
- Active-Active архитектура с георезервированием (2 зоны доступности)
- Независимые Kubernetes кластеры в каждой зоне
- Многоуровневая балансировка (GSLB → ALB → Ingress → Service)
- PostgreSQL Patroni с автоматическим failover
- HPA и Cluster Autoscaler для автомасштабирования

**Результаты:**
- Целевая доступность: 99.95%+
- RTO для отказа зоны: 10-30 секунд
- Поддержка до 1000+ RPS с автомасштабированием

---

### [Task 2: Динамическое масштабирование в Kubernetes](./task2/)

**Цель:** Решить проблему нестабильной работы в периоды пиковой нагрузки.

**Реализовано:**
1. **HPA по памяти** — масштабирование на основе утилизации памяти (встроенная метрика)
2. **HPA по RPS** — масштабирование на основе запросов в секунду (кастомная метрика из Prometheus)

**Компоненты:**
- Minikube + Metrics Server
- Prometheus + Prometheus Adapter
- Locust для нагрузочного тестирования

**Результаты:**
- Масштабирование по RPS быстрее (30-60 сек) и точнее, чем по памяти (2-3 мин)
- Снижение RPS в 2-3 раза после уменьшения нагрузки
- Равномерное распределение нагрузки между подами

**Альтернативы:** VPA для stateful приложений, KEDA для event-driven систем

---

### [Task 3: Переход на Event-Driven архитектуру](./task3/)

**Цель:** Устранить проблемы синхронной зависимости между сервисами при планируемом росте (удвоение страховых компаний).

**Проблемы текущей архитектуры:**
- Синхронные REST-запросы между сервисами
- Каскадные сбои при отказе одного сервиса
- Время отклика растёт пропорционально количеству интеграций
- Неэффективное использование ресурсов

**Решение:**
- **Apache Kafka** как брокер событий
- **Паттерн Transactional Outbox** для надежной публикации событий
- **Репликация данных через события** вместо синхронных запросов
- Асинхронная модель работы сервисов

**Топики событий:**
- `insurance-products` — изменения страховых продуктов
- `insurance-policies` — создание/изменение полисов
- `client-data` — изменения данных клиентов

**Преимущества:**
- Независимое масштабирование сервисов
- Изоляция сбоев
- Снижение времени отклика для пользователей
- Гарантированная доставка событий
- Near real-time актуальность данных

### [Task 4: Проектирование продажи ОСАГО](./task4/)

**Цель:** Спроектировать систему оформления ОСАГО с real-time отображением предложений.

**Требования:**
- Real-time отображение предложений по мере поступления
- До 2500 одновременных пользователей в пик
- Максимальное время ожидания от страховой — 60 секунд
- 5 страховых компаний с REST API

**Архитектурные решения:**
- **WebSocket** для real-time стриминга предложений (клиент ↔ core-app ↔ osago-aggregator)
- **REST** для стандартных CRUD операций
- Собственная БД для osago-aggregator (заявки, предложения, Outbox)

**Паттерны отказоустойчивости:**
- ⏱️ **Rate Limiting** — на API Gateway (защита от перегрузки)
- ⏱️ **Timeout** — 60 секунд на запрос к страховой
- 🔄 **Retry** — 3 попытки с exponential backoff
- 🔒 **Circuit Breaker** — отдельный для каждой страховой компании
- 🏗️ **Bulkhead** — изоляция пулов соединений

**Преимущества:**
- Мгновенное отображение предложений по мере получения
- Изоляция сбоев (отказ одной страховой не влияет на другие)
- Быстрый failover (10 секунд в Circuit Breaker)
- Горизонтальное масштабирование всех компонентов

---

### [Task 5: Проектирование GraphQL API](./task5/)

**Цель:** Решить проблему высокой вариативности запрашиваемых данных для сервиса client-info.

**Проблема:**
- Карточка клиента содержит ~500 атрибутов
- Разные потребители требуют разные наборы данных
- REST API создаёт множественные запросы (до 3 на сценарий)
- Over-fetching и under-fetching данных

**Решение:**
- **GraphQL API** с единым эндпоинтом `client(id)`
- Клиент сам определяет нужные поля в запросе
- Типы: `Client`, `Document`, `Relative`

**Преимущества:**
- Снижение RPS в 2-3 раза (1 запрос вместо 3)
- Устранение over-fetching (только нужные поля из 500)
- Устранение under-fetching (всё в одном запросе)
- Гибкость для разных потребителей
- Упрощение эволюции API (backward compatibility)

---

### [Task 6: Настройка Rate Limiting](./task6/)

**Цель:** Защитить систему от перегрузки партнёром, превышающим лимиты (250 RPS вместо 20).

**Решение:**
- **Rate Limiting** на уровне NGINX балансировщика
- Лимит: 10 запросов в минуту на IP-адрес
- Код ошибки: 429 (Too Many Requests)

**Конфигурация:**
```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/m;
limit_req zone=api_limit;
limit_req_status 429;
```

**Преимущества:**
- Запросы фильтруются до попадания в приложение
- Экономия ресурсов backend-серверов
- Единая точка контроля
- Справедливое распределение ресурсов между клиентами

## 🛠 Технологический стек

### Инфраструктура
- **Kubernetes** — оркестрация контейнеров
- **Docker** — контейнеризация
- **NGINX** — балансировка и rate limiting
- **HAProxy** — балансировка БД

### База данных
- **PostgreSQL** — основная БД
- **Patroni** — HA для PostgreSQL
- **etcd** — координация кластера

### Event Streaming
- **Apache Kafka** — брокер событий
- **Transactional Outbox** — надежная публикация событий

### Масштабирование
- **HPA** (Horizontal Pod Autoscaler) — масштабирование подов
- **Cluster Autoscaler** — масштабирование узлов
- **Metrics Server** — сбор метрик

### Мониторинг
- **Prometheus** — сбор метрик
- **Grafana** — визуализация
- **Alertmanager** — алерты
- **Loki** — логи
- **Jaeger** — трейсинг

### Отказоустойчивость
- **Resilience4j** — Circuit Breaker, Retry, Timeout, Bulkhead
- **Redis** — shared state, кеширование

### API
- **REST** — для стандартных операций
- **WebSocket** — для real-time взаимодействия
- **GraphQL** — для гибких запросов с большим количеством атрибутов
