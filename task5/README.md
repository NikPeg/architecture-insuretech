# Задание 5. Проектирование GraphQL API для сервиса client-info

## Описание проблемы

Сервис управления клиентскими данными `client-info` столкнулся с проблемой высокой вариативности запрашиваемых данных:

- Карточка клиента содержит около **500 атрибутов**
- Разные потребители (веб-приложение, сервис core-app) требуют **разные наборы данных** в разных сценариях
- Текущая REST реализация предоставляет **множество отдельных ресурсов** (контакты, документы, родственники и т.д.)
- Это приводит к **кратному увеличению нагрузки и RPS** на сервис

### Проблемы существующего REST API

1. **Множественные запросы**: Для получения полной информации о клиенте требуется 3 отдельных HTTP запроса:
   - `GET /clients/{id}` - базовая информация
   - `GET /clients/{id}/documents` - документы
   - `GET /clients/{id}/relatives` - родственники

2. **Over-fetching**: Если предоставить один общий эндпоинт со всеми данными, будет передаваться избыточный объем данных (500 атрибутов), что замедлит взаимодействие

3. **Under-fetching**: При использовании разделенных эндпоинтов требуется делать множественные запросы

4. **Высокий RPS**: Каждый сценарий генерирует несколько запросов к серверу

## Решение: GraphQL API

GraphQL решает эти проблемы благодаря своей гибкости - клиент сам определяет, какие именно данные ему нужны в конкретном сценарии.

### Структура GraphQL схемы

Схема определена в файле `client-info.graphql` и включает:

#### 1. Типы данных

**Client** - основная сущность клиента
```graphql
type Client {
  id: ID!
  name: String!
  age: Int!
  documents: [Document!]!
  relatives: [Relative!]!
}
```

**Document** - документ клиента
```graphql
type Document {
  id: ID!
  type: String!
  number: String!
  issueDate: String!
  expiryDate: String
}
```

**Relative** - родственник клиента
```graphql
type Relative {
  id: ID!
  relationType: String!
  name: String!
  age: Int!
}
```

#### 2. Запросы (Queries)

```graphql
type Query {
  client(id: ID!): Client
}
```

Один универсальный запрос `client` покрывает все три операции REST API.

### Примеры использования

#### Сценарий 1: Только базовая информация о клиенте

**REST** (1 запрос):
```
GET /clients/123
```

**GraphQL** (1 запрос, но меньше данных):
```graphql
query {
  client(id: "123") {
    id
    name
    age
  }
}
```

#### Сценарий 2: Клиент с документами

**REST** (2 запроса):
```
GET /clients/123
GET /clients/123/documents
```

**GraphQL** (1 запрос):
```graphql
query {
  client(id: "123") {
    id
    name
    documents {
      id
      type
      number
      issueDate
      expiryDate
    }
  }
}
```

#### Сценарий 3: Полная информация

**REST** (3 запроса):
```
GET /clients/123
GET /clients/123/documents
GET /clients/123/relatives
```

**GraphQL** (1 запрос):
```graphql
query {
  client(id: "123") {
    id
    name
    age
    documents {
      id
      type
      number
      issueDate
      expiryDate
    }
    relatives {
      id
      relationType
      name
      age
    }
  }
}
```

#### Сценарий 4: Только нужные поля документов

**GraphQL** (выборочные поля):
```graphql
query {
  client(id: "123") {
    name
    documents {
      type
      number
    }
  }
}
```

## Преимущества GraphQL решения

### 1. Снижение количества запросов
- **Было**: 3 отдельных REST запроса для получения полной информации
- **Стало**: 1 GraphQL запрос с выборкой нужных данных
- **Результат**: Снижение RPS на сервис в 2-3 раза для типичных сценариев

### 2. Устранение over-fetching
- Клиент запрашивает **только те поля**, которые ему нужны
- Не передаются лишние данные из 500 атрибутов
- **Результат**: Снижение объема передаваемых данных, ускорение взаимодействия

### 3. Устранение under-fetching
- Один запрос может получить данные из нескольких связанных сущностей
- Не нужно делать дополнительные запросы
- **Результат**: Уменьшение задержек, улучшение производительности

### 4. Гибкость для разных потребителей
- Веб-приложение и core-app могут использовать **один API**
- Каждый запрашивает только то, что ему нужно в конкретном сценарии
- **Результат**: Упрощение поддержки, один унифицированный интерфейс

### 5. Снижение нагрузки на сеть
- Меньше HTTP запросов = меньше overhead на установку соединений
- Меньше передаваемых данных = меньше трафика
- **Результат**: Особенно важно для мобильных клиентов

### 6. Упрощение эволюции API
- Новые поля добавляются без breaking changes
- Старые поля могут быть помечены как `@deprecated`
- **Результат**: Backward compatibility из коробки

## Сравнение с REST

| Критерий | REST | GraphQL |
|----------|------|---------|
| Количество запросов | 1-3 на сценарий | 1 на любой сценарий |
| Over-fetching | Да, получаем все поля | Нет, выбираем нужные |
| Under-fetching | Да, нужны доп. запросы | Нет, всё в одном запросе |
| RPS на сервис | Высокий | Снижен в 2-3 раза |
| Объём данных | Фиксированный | Только запрошенные |
| Сложность клиента | Простая | Требует GraphQL клиент |
| Кеширование | HTTP кеш из коробки | Требует дополнительной настройки |

## Рекомендации по реализации

### 1. На стороне сервера (backend)

- Использовать **DataLoader** для batch загрузки данных и предотвращения N+1 проблемы
- Реализовать **пагинацию** для больших списков документов/родственников (если потребуется)
- Настроить **rate limiting** на уровне GraphQL запросов
- Внедрить **мониторинг** сложности запросов и времени выполнения

### 2. На стороне клиента (frontend)

- Использовать **Apollo Client** или **Relay** для кеширования
- Применять **постоянные запросы** (Persisted Queries) для оптимизации и безопасности
- Использовать **фрагменты** для переиспользования частей запросов

### 3. Кеширование

Поскольку GraphQL не поддерживает стандартное HTTP кеширование, рекомендуется:
- **Кеширование на клиенте** через Apollo Client
- **Постоянные запросы** (Persisted Queries) для возможности HTTP кеширования
- **Кеширование по хешу запроса** на уровне API Gateway

4. ✅ Улучшить производительность взаимодействия
