# Анализ проблем и рисков текущей архитектуры InsureTech

## Текущая ситуация

Сервисы **core-app** и **ins-comp-settlement** получают данные о страховых продуктах через REST API сервиса **ins-product-aggregator**. При каждом запросе ins-product-aggregator:
- Синхронно запрашивает информацию из всех страховых компаний (сейчас 5)
- Агрегирует данные в единый список
- Возвращает результат в рамках синхронного запроса

**Частота обращений:**
- **core-app**: каждые 15 минут
- **ins-comp-settlement**: раз в сутки (ночью)

**Дополнительно:** ins-comp-settlement раз в сутки запрашивает через REST API из core-app все оформленные за день страховки.

**Планируемые изменения:** Количество страховых компаний увеличится с 5 до 10 (в 2 раза).

---

## Выявленные проблемы

### 1. Синхронная зависимость между сервисами

**Проблема:** Сервисы core-app и ins-comp-settlement синхронно зависят от ins-product-aggregator, который в свою очередь синхронно зависит от API всех страховых компаний.

**Последствия:**
- При недоступности одной из страховых компаний весь запрос может завершиться ошибкой или тайм-аутом
- Время отклика ins-product-aggregator равно сумме времени запросов ко всем страховым компаниям
- Ошибки в работе ins-product-aggregator напрямую влияют на работу core-app и ins-comp-settlement

### 2. Масштабируемость и производительность

**Проблема:** При увеличении количества страховых компаний в 2 раза (с 5 до 10) пропорционально увеличится время обработки запросов.

**Последствия:**
- Время отклика на запросы к ins-product-aggregator может увеличиться до неприемлемых значений
- Пользователи core-app будут дольше ждать получения актуальных данных о продуктах
- Повышается вероятность тайм-аутов при синхронных запросах
- Необходимость пропорционального масштабирования ресурсов всех зависимых сервисов

### 3. Отказоустойчивость

**Проблема:** Отказ или замедление работы одной страховой компании влияет на весь процесс агрегации данных.

**Последствия:**
- Недоступность API одной страховой компании может блокировать получение данных от всех остальных
- Медленная работа одной страховой компании увеличивает общее время отклика
- Сервисы потребители вынуждены ожидать завершения всех запросов
- Отсутствие механизма частичной доступности данных

### 4. Неэффективное использование ресурсов

**Проблема:** Повторные запросы одних и тех же данных с небольшими интервалами (каждые 15 минут для core-app).

**Последствия:**
- Избыточная нагрузка на ins-product-aggregator
- Избыточная нагрузка на API страховых компаний
- Неэффективное использование сетевых ресурсов
- Потенциальное превышение лимитов rate limiting на стороне страховых компаний

### 5. Проблема двойной записи

**Проблема:** При изменении состояния в БД и необходимости уведомить другие сервисы через REST API возникает риск частичной операции.

**Последствия для взаимодействия ins-comp-settlement и core-app:**
- Данные могут быть сохранены в БД, но запрос в другой сервис может завершиться ошибкой
- Несогласованность данных между сервисами
- Сложность отката операций
- Необходимость ручного вмешательства для восстановления целостности данных

### 6. Тесная связанность компонентов

**Проблема:** Сервисы знают друг о друге и о структуре API, что создает тесную связанность.

**Последствия:**
- Изменения в ins-product-aggregator требуют обновления потребителей
- Усложняется независимая разработка и развертывание сервисов
- Сложно добавлять новых потребителей данных о продуктах
- Версионирование API становится критичным

---

## Риски при масштабировании (10 страховых компаний)

### 1. Критическое увеличение времени отклика

**Риск:** При удвоении количества страховых компаний время отклика может увеличиться вдвое или более, что неприемлемо для пользовательского опыта.

**Вероятность:** Высокая  
**Влияние:** Критическое

### 2. Каскадные сбои

**Риск:** Проблемы в одной страховой компании могут привести к цепочке сбоев во всех зависимых сервисах.

**Вероятность:** Высокая  
**Влияние:** Высокое

### 3. Превышение лимитов API страховых компаний

**Риск:** Частые синхронные запросы к API страховых компаний могут привести к превышению rate limits.

**Вероятность:** Средняя  
**Влияние:** Высокое

### 4. Невозможность горизонтального масштабирования

**Риск:** При синхронной архитектуре масштабирование одного компонента требует масштабирования всех зависимых компонентов.

**Вероятность:** Высокая  
**Влияние:** Высокое

### 5. Сложность мониторинга и диагностики

**Риск:** При сложной цепочке синхронных вызовов становится трудно определить источник проблемы.

**Вероятность:** Средняя  
**Влияние:** Среднее

### 6. Потеря данных при сбоях

**Риск:** При двойных операциях записи (БД + REST API) возможна потеря данных или их несогласованность.

**Вероятность:** Средняя  
**Влияние:** Критическое

---

## Ключевые проблемы для решения

1. **Разорвать синхронные зависимости** между сервисами
2. **Реализовать асинхронную репликацию данных** через события
3. **Обеспечить отказоустойчивость** при проблемах с отдельными страховыми компаниями
4. **Снизить нагрузку** на ins-product-aggregator и API страховых компаний
5. **Обеспечить согласованность данных** при публикации событий
6. **Улучшить масштабируемость** всех компонентов системы

---

## Рекомендации по решению

### 1. Переход на Event-Driven архитектуру

**Решение:** Использовать брокер сообщений (например, Apache Kafka или RabbitMQ) для асинхронной передачи данных между сервисами.

**Преимущества:**
- Разрыв синхронных зависимостей
- Независимое масштабирование сервисов
- Повышение отказоустойчивости
- Снижение времени отклика основных операций

### 2. Применение паттерна репликации данных через события

**Решение:** 
- ins-product-aggregator публикует события об изменении данных о продуктах
- core-app и ins-comp-settlement подписываются на эти события и поддерживают локальные реплики данных
- Устраняется необходимость в периодических синхронных запросах

**Преимущества:**
- Актуальность данных в реальном времени
- Снижение нагрузки на ins-product-aggregator
- Независимость потребителей от доступности поставщика данных
- Возможность добавления новых потребителей без изменения архитектуры

### 3. Использование паттерна Transactional Outbox

**Решение:** Для обеспечения надежной публикации событий при изменении данных в БД использовать паттерн Transactional Outbox.

**Применение:**
- При обновлении данных о продуктах в БД события сохраняются в Outbox-таблицу в рамках одной транзакции
- Отдельный процесс (Polling Publisher или CDC) вычитывает события из Outbox и публикует их в брокер
- Гарантируется согласованность: если данные сохранились в БД, событие точно будет опубликовано

**Преимущества:**
- Решение проблемы двойной записи
- Гарантия доставки событий
- Атомарность операций
- Возможность аудита всех изменений

### 4. Изменение логики работы ins-product-aggregator

**Решение:** 
- Перевести ins-product-aggregator на асинхронный режим работы
- Периодически (например, раз в час или при получении событий от страховых компаний) агрегировать данные
- Публиковать события об изменении продуктов в брокер
- Обрабатывать недоступность отдельных страховых компаний без блокировки всего процесса

**Преимущества:**
- Изоляция сбоев отдельных страховых компаний
- Более эффективное использование ресурсов
- Снижение нагрузки на API страховых компаний
- Возможность публикации частичных обновлений

### 5. Изменение взаимодействия ins-comp-settlement и core-app

**Решение:**
- core-app публикует события о создании новых страховок
- ins-comp-settlement подписывается на эти события и собирает реплику данных
- Устраняется необходимость в ежедневном синхронном запросе

**Преимущества:**
- Данные доступны в реальном времени
- Снижение нагрузки на core-app
- Отсутствие ночных пиковых нагрузок
- Возможность формирования отчетов в любое время

---

## Выводы

Текущая синхронная архитектура не готова к планируемому росту количества страховых компаний. Переход на Event-Driven архитектуру с использованием паттерна Transactional Outbox позволит:

1. ✅ Обеспечить масштабируемость при росте до 10+ страховых компаний
2. ✅ Повысить отказоустойчивость системы
3. ✅ Снизить время отклика для конечных пользователей
4. ✅ Обеспечить согласованность данных
5. ✅ Упростить добавление новых потребителей данных
6. ✅ Улучшить мониторинг и диагностику проблем

Рекомендуется реализовать Event-Driven архитектуру с использованием брокера сообщений (Kafka) и паттерна Transactional Outbox для обеспечения надежной публикации событий.
