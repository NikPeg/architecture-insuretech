# Задание 3: Переход на Event-Driven архитектуру

## Описание задания

Проанализировать текущую архитектуру взаимодействия сервисов InsureTech и предложить решение на основе Event-Driven архитектуры для устранения выявленных проблем и рисков, связанных с планируемым ростом нагрузки (увеличение количества страховых компаний с 5 до 10).

## Состав решения

### 1. Анализ проблем и рисков

**Файл:** `Проблемы_и_риски.md`

Подробный анализ текущей архитектуры с выявлением:
- Проблем синхронной зависимости между сервисами
- Проблем масштабируемости и производительности
- Рисков отказоустойчивости
- Проблем неэффективного использования ресурсов
- Рисков при масштабировании до 10 страховых компаний

**Ключевые выводы:**
- Текущая синхронная REST-архитектура не готова к планируемому росту
- При удвоении количества страховых компаний время отклика может увеличиться вдвое
- Отказ одной страховой компании может привести к каскадным сбоям
- Необходим переход на асинхронную Event-Driven архитектуру

### 2. Решение: Event-Driven архитектура

**Файл:** `Решение_Event_Driven_архитектура.md`

Подробное описание предлагаемого решения, включающее:

#### Ключевые изменения:
- **Внедрение Apache Kafka** как брокера событий
- **Применение паттерна Transactional Outbox** для надежной публикации событий
- **Репликация данных через события** вместо синхронных REST-запросов
- **Асинхронная модель работы** ins-product-aggregator

#### Топики событий:
- `insurance-products` — события об изменении страховых продуктов
- `insurance-policies` — события о создании/изменении страховок
- `client-data` — события об изменении данных клиентов

#### Паттерн Transactional Outbox:
- Решение проблемы двойной записи (БД + брокер событий)
- Гарантия атомарности: если изменения в БД зафиксированы, событие будет опубликовано
- Реализация через Polling Publisher или Transaction Log Tailing (CDC)

#### Преимущества решения:
✅ Независимое масштабирование сервисов  
✅ Изоляция сбоев отдельных компонентов  
✅ Снижение времени отклика для пользователей  
✅ Гарантированная доставка событий  
✅ Актуальность данных в near real-time  

### 3. Диаграмма Event-Driven архитектуры

**Файлы:** 
- `architecture_event_driven.mmd` — исходная диаграмма в формате Mermaid
- `architecture_event_driven.png` — скомпилированная диаграмма (2400x2000px, высокое качество)

**Обновленная диаграмма контейнеров (C4 Model) показывает:**

#### Компоненты:
1. **Frontend Layer:**
   - InsureTech Web (JavaScript, React)

2. **Core Services:**
   - **client-info** — сервис управления клиентскими данными
   - **core-app** — монолитное приложение с локальной репликой данных о продуктах
   - **ins-product-aggregator** — агрегатор данных с функцией publisher событий
   - **ins-comp-settlement** — сервис взаиморасчетов с локальными репликами

3. **Event Streaming Platform:**
   - **Apache Kafka** — брокер событий с топиками для продуктов, страховок и клиентов

4. **Data Layer:**
   - **core-db** — PostgreSQL с Outbox-таблицей
   - **ins-product-agg-db** — PostgreSQL с Outbox-таблицей
   - **ins-comp-settlement-db** — PostgreSQL для реплик

#### Потоки событий:
- `ins-product-aggregator` → **Kafka** → `core-app`, `ins-comp-settlement`
- `core-app` → **Kafka** → `ins-comp-settlement`
- `client-info` → **Kafka** → другие потребители

#### Внешние интеграции:
- Асинхронные запросы к страховым компаниям (периодически)
- Устранены синхронные зависимости между внутренними сервисами

**Диаграмма также отражает:**
- Потоки событий от Publishers через Kafka к Consumers
- Применение паттерна Transactional Outbox для надежной публикации
- Роль PostgreSQL с Outbox-таблицами
- Асинхронное взаимодействие со страховыми компаниями

## Применение паттерна Transactional Outbox

Для обеспечения надежной публикации событий используется паттерн **Transactional Outbox**, который решает проблему двойной записи (БД + брокер событий) и гарантирует атомарность операций.

### Применяется в сервисах:
✅ **ins-product-aggregator** — публикация событий об изменении продуктов  
✅ **core-app** — публикация событий о создании страховок  
✅ **client-info** — публикация событий об изменении клиентских данных  

### Гарантии паттерна:
- ✅ Атомарность: либо обе операции выполнены, либо обе откачены
- ✅ Событие будет опубликовано, даже если брокер временно недоступен
- ✅ Нет потери данных при сбоях
- ✅ Возможность аудита всех изменений

**Подробное описание** паттерна Transactional Outbox, включая структуру таблиц, примеры кода и варианты реализации Message Relay (Polling Publisher и CDC), см. в документе `Решение_Event_Driven_архитектура.md`.

## Сравнение: Было vs Стало

### Получение данных о продуктах в core-app

| Аспект | Было | Стало |
|--------|------|-------|
| Частота обновления | Каждые 15 минут | Near real-time |
| Зависимость от aggregator | Критическая | Отсутствует |
| Время отклика | Сетевой запрос | Локальная БД (мгновенно) |
| Актуальность данных | Задержка до 15 минут | Секунды |

### Получение данных о страховках в ins-comp-settlement

| Аспект | Было | Стало |
|--------|------|-------|
| Частота обновления | Раз в сутки (ночью) | Непрерывно |
| Зависимость от core-app | Критическая | Отсутствует |
| Пиковая нагрузка | Высокая (ночью) | Равномерная |
| Доступность данных | После обновления | Всегда актуальны |

## Мониторинг

### Ключевые метрики:

**Outbox Message Relay:**
- Количество необработанных событий в Outbox (норма < 100)
- Средняя задержка публикации (норма < 500ms)
- Количество ошибок публикации

**Kafka:**
- Consumer lag (норма < 100 событий)
- Throughput (события/сек)
- Состояние партиций и реплик

**Потребители:**
- Время обработки события (P95 < 100ms)
- Количество ошибок обработки
- Количество обработанных событий
